# Стековані гілки

Стек — це ланцюжок гілок, де кожна будується на тій, що під нею:
`main → api → ui`. Переглянути три невеликі PR приємніше, ніж один величезний.

![Стек гілок](../../screenshots/branch-stack.webp)

Gitcito показує стек знизу вгору з кількістю комітів на кожному рівні. Кожен
рівень із відкритим PR носить його номер як чип — натисніть на нього, щоб
відкрити PR.

## Надішліть стек як зв’язані PR

**Надіслати стек як PR** робить одним кліком те, за що інструменти для стеків
беруть гроші:

1. Пушить кожен рівень із `--force-with-lease` (свіжі гілки це терплять,
   а перескладеним воно необхідне).
2. Відкриває PR для кожного рівня, де його немає — кожен **на основі
   батьківської гілки**, а не `main`, тож кожне рев’ю показує лише власні
   коміти. Заголовок і опис беруться з комітів самого рівня.
3. Перенацілює наявні PR, чия база з’їхала.
4. Записує в тіло кожного PR **розділ навігації по стеку**, щоб рев’юер на
   будь-якому рівні бачив увесь ланцюжок і місце цього PR у ньому.

Дія **ідемпотентна**: натискайте її після кожного перескладання, нового рівня
чи злитого PR — вона сходиться: ніщо не дублюється, зачіпається лише те, що
з’їхало.

Коли нижній PR **злито**, та сама кнопка прибирає за ним: нащадок злитого
рівня перечіплюється на основну гілку, рівень прибирається зі стеку, його
локальна гілка видаляється (це безпечно — основна гілка доказово її містить),
ланцюжок перескладається, а всі решта PR перенацілюються. Зливайте знизу
вгору, натискайте «Надіслати», повторюйте.

## Перескладання

Коли змінюється нижня гілка — ви врахували зауваження рев’ю в `api` — усі гілки
над нею тепер побудовані на неправильній основі. **Перескласти** каскадом робить
ребейз усього ланцюжка через `rebase --onto`, тож переписування батьківської
гілки не дублює коміти в її нащадках. Після перескладання натисніть
**Надіслати** ще раз: переписані рівні буде запушено примусово, і PR оновляться
на місці.

## Обмеження

- Надсилання поки працює **лише з GitHub** (створення працює на всіх чотирьох
  хостах, але перенацілення й оновлення тіла потребують API GitHub).
- Прибирання після злиття низу бачить звичайні злиття і злиття через ребейз за
  походженням, а **squash**-злиття — запитуючи GitHub, чи приземлився
  pull-реквест гілки; тож із токеном GitHub прибирається будь-який стиль
  злиття. На інших хостах або без токена рівень, злитий через squash, усе ще
  доведеться прибрати зі стеку вручну. І спершу зробіть fetch — перевірка
  походження читає основну гілку станом на ваш останній fetch.
- Розділ стеку в тілі PR підтримується між прихованими маркерами — ваш власний
  опис над ним зберігається.

## Де живуть зв’язки

Зв’язки з батьківськими гілками зберігаються в **конфігурації git**, тож вони
подорожують разом із репозиторієм і переживають повторне клонування. Ніщо не
живе в жодному сервісі.
