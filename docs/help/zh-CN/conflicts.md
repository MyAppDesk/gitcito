# 解决冲突

当一次合并、变基、拣选（cherry-pick）或还原停下来时，横幅会告诉你**是什么**停了下来，以及**在什么和什么之间**——写的是「正在把 `feature/x` 合并进 `main`」，而不是干巴巴一句「冲突」。

![冲突解决器](../../screenshots/conflict-resolver.webp)

## 为什么这里会冲突

标题栏里的**为什么这里会冲突**，会分别按两边列出：自两个分支分道扬镳以来，动过这个文件的那些提交——也就是 `git log --merge`，git 早就自带、却没人找得到的东西。

![来自两边、动过这个冲突文件的提交](../../screenshots/conflict-why.webp)

冲突标记告诉你哪些内容打了架。这里告诉你是谁改的、为什么改，而后者通常才是真正决定该怎么解的东西。这里什么都没有，说明两边都没有对这个确切路径提交过改动——这场冲突来自一次重命名或移动。

## 三个栏

| 栏 | 是什么 |
|---|---|
| 左 | **我们的（Ours）**——你原本所在的那一边，标注了它的提交 |
| 右 | **他们的（Theirs）**——正在并进来的那一边，标注了它的提交 |
| 中 | **输出**：可编辑，带行号，也是真正会被暂存的内容 |

三个栏都能调整宽度。

## 挑选

可以按**行**、按**块**，或者一次拿下**整整一边**——而且当答案是「两边都留」的时候，你可以把一个块的两边都收下。一个逐个冲突的导航器会带你走完还剩下的部分，所以你不可能不小心漏下一个标记。

## AI 协助

启用 AI 后，**用 AI 解决**会往输出栏里提出一份合并方案。它绝不会自己应用任何东西：你来读、你来改、你来暂存。参见 [AI 功能](ai.md)。

## 从一开始就避开它们

[冲突雷达](conflict-radar.md)会在你合并任何分支之前，先告诉你哪些分支将会冲突。

## 让 git 帮你记住（rerere）

对一个长期存在的分支做变基，你每次都会撞上同一个冲突。`rerere`——*reuse recorded resolution*，复用已记录的解决方案——就是 git 的答案：它记住你当初是怎么了结某个冲突的，并在下次出现一模一样的冲突时把那个答案重放一遍。

**设置 → 通用 → 记住冲突的解决方案。** 它会把 `rerere.enabled` 写进你的全局 git 配置，所以命令行也会有同样的行为。

当 git 替你作答之后，解决器会明说这件事，而不是给你看一个空空如也的「没有冲突标记」界面，同时提供**忘掉这个解决方案**——它会丢掉那份记忆*并且*把冲突原样带回来，好让你换个方式了结它。

有两件事值得知道：

- **被重放的解决方案不会自动暂存**，除非你打开*自动暂存被重放的解决方案*。让它保持关闭：这次停顿的意义就在于，一个记住的答案在这一次特定的合并里可能是错的，而不看一眼就暂存，正是它混进提交的途径。

  这也是为什么被重放的文件**仍然留在「有冲突的文件」里**：git 写好了内容，但索引里它仍然处于未合并状态，只有暂存才能了结这一点。用解决器里的**按现状暂存**，或者列表里的**全部标记为已解决**，才能让它挪窝。
- **rerere 并不理解每一种冲突。** 添加/添加与删除/修改这两类冲突拿不到预映像，所以它们每次都会原样回来。设置里的计数是它实际记住的条数，而**全部忘掉**会清空它。
