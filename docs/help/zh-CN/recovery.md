# 恢复与 reflog

Git 很少真的丢东西。难的是把它重新找回来。

## Reflog

`HEAD` 的每一次移动——以及每个分支的每一次移动——连同造成它的原因：检出、重置、变基、
修补、一次强制获取。从任何一条过去的记录，你都可以**检出它**、**从它建分支**，或者
**硬重置到它**。

![reflog 查看器](../../screenshots/reflog.webp)

这就是那个「我刚刚重置错了分支」按钮。

## WIP 快照

未提交的工作是 reflog 唯一救不了的东西，所以 Gitcito 会为它拍快照：你已跟踪的改动加上
已暂存的索引，作为一个 `git stash create` 提交捕获下来，钉在 `refs/gitcito/wip` 下面。

![WIP 快照](../../screenshots/snapshots.webp)

- 它**从不碰你的工作区**，也**从不出现在你的贮藏列表里**——它是一个隐藏的引用，不是
  贮藏。
- 你可以手动拍一张，也可以让它每 **5 / 15 / 30 分钟** 自动跑一次。
- 列表里的任何一张快照都可以恢复或删除。

## 引导式二分查找

把提交标为好或坏，看着范围一步步收窄，最后落在第一个坏提交上。Gitcito 会跟踪还剩多少
步，所以你知道自己离答案是两个问题还是十个问题。

![引导式二分查找](../../screenshots/bisect.webp)

### 让一条命令来判定

范围一旦定下，**让一条命令来判定**就把整个搜索交给 `git bisect run`。Git 会检出每一个
候选提交，运行你的命令，然后读它的退出码：

| 退出码 | 含义 |
|-----------|-------|
| `0` | 好——问题不在这里 |
| `125` | 这个测不了；跳过它 |
| 其他任何值 | 坏 |

一套测试用例本来就说这门语言，所以 `npm test` 通常就是全部答案。Gitcito 会把本项目
自己的脚本作为一键填入的选项提供出来，在运行时把输出流式显示出来，然后在你一个问题都
不用回答的情况下落到第一个坏提交上。

![命令输入框，准备把搜索交给一套测试用例](../../screenshots/bisect-run.webp)

**要留神的地方。** 这条命令会在 git 测试的*每一个*提交上运行，所以一条会部署、发布，
或者往仓库外面写东西的命令，会把那件事干上好几遍。让它只做读取和报告。**停止**会杀掉
这次运行但保留会话，这样你可以继续手动标记；**中止**则彻底结束这次二分查找。

一条因为无关原因而失败的命令——比方说历史上那个时点缺少某个依赖——会把一个好提交标成
坏的，把搜索引到错误的地方去。在包装脚本里以 `125` 退出，就是 git 给出的解法。

## 撤销 / 重做

大多数操作都会往撤销栈里压一条记录，所以在 git 允许的范围内，<kbd>⌘Z</kbd> 会回退最近
的那一次。
