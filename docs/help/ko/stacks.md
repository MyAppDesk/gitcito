# 스택 브랜치

스택은 각 브랜치가 아래 브랜치 위에 쌓이는 사슬이에요. `main → api → ui` 처럼요.
작은 PR 세 개를 리뷰하는 편이 거대한 PR 하나를 리뷰하는 것보다 나아요.

![브랜치 스택](../../screenshots/branch-stack.webp)

Gitcito는 스택을 아래에서 위로 보여 주면서 각 단계의 커밋 수를 함께 표시해요.
열린 PR이 있는 단계는 그 번호를 칩처럼 달고 있어요 — 클릭하면 해당 PR이 열려요.

## 스택을 연쇄 PR로 제출하기

**스택을 PR로 제출**은 스택 도구들이 돈을 받고 파는 일을 클릭 한 번으로 해내요.

1. 모든 단계를 `--force-with-lease` 로 푸시해요(새 브랜치는 그냥 받아들이고,
   재적재된 브랜치에는 이게 꼭 필요해요).
2. PR이 없는 모든 단계에 PR을 열어요 — 각각 `main` 이 아니라 **부모 브랜치를
   기반으로** 하기 때문에, 모든 리뷰에는 자기 커밋만 보여요. 제목과 설명은 그
   단계 자신의 커밋에서 만들어져요.
3. 기반이 어긋난 기존 PR의 대상을 바로잡아요.
4. 모든 PR 본문에 **스택 내비게이션 섹션**을 적어 넣어서, 어느 단계의 리뷰어든
   사슬 전체와 이 PR이 그 안 어디에 있는지 볼 수 있어요.

이 동작은 **멱등**이에요. 재적재하거나 단계를 새로 얹거나 PR이 병합될 때마다
눌러도 결과는 수렴해요 — 아무것도 중복되지 않고, 어긋난 것만 손대요.

맨 아래 PR이 **병합**되면 같은 버튼이 뒷정리까지 해 줘요. 병합된 단계의 자식은
트렁크 위로 부모가 바뀌고, 그 단계는 추적이 해제되고, 로컬 브랜치는 삭제돼요
(안전해요 — 트렁크가 그걸 담고 있다는 게 증명되니까요). 그리고 사슬이 재적재되고
남은 PR의 대상이 모두 바로잡혀요. 아래에서 위로 병합하고, 제출을 누르고,
반복하세요.

## 재적재

아래쪽 브랜치가 바뀌면 — 예를 들어 `api` 의 리뷰 의견을 반영했다면 — 그 위의 모든
브랜치는 이제 잘못된 기반 위에 놓여 있어요. **재적재**는 `rebase --onto` 로 사슬
전체를 연쇄적으로 리베이스해서, 부모를 다시 쓴 결과가 자식들에 커밋을 중복시키지
않도록 해요. 재적재한 뒤에는 **제출**을 다시 누르세요. 다시 쓴 단계들이 강제
푸시되고 PR들이 제자리에서 갱신돼요.

## 한계

- 제출은 아직 **GitHub 전용**이에요(생성은 네 호스트 모두에서 되지만, 대상 변경과
  본문 갱신에는 GitHub API가 필요해요).
- 맨 아래 병합 뒤처리는 merge와 rebase 병합은 조상 관계로 알아보고,
  **스쿼시(squash)** 병합은 그 브랜치의 PR이 병합됐는지 GitHub에 물어봐서
  알아봐요 — 그래서 GitHub 토큰만 있으면 어떤 병합 방식이든 정리돼요. 다른
  호스트에서, 또는 토큰이 없으면 스쿼시로 병합된 단계는 여전히 직접 추적을
  해제해야 해요. 그리고 먼저 페치하세요 — 조상 관계 확인은 마지막 페치 시점의
  트렁크를 읽어요.
- PR 본문의 스택 섹션은 숨은 표식 사이에서 관리돼요 — 그 위에 적은 여러분의 설명은
  그대로 보존돼요.

살아남아요. 어떤 서비스에도 아무것도 남지 않아요.
