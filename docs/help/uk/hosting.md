# Хостинг та pull-реквести

## Створення

Створіть pull- (або merge-) реквест, не покидаючи застосунку: випадні списки
гілок, заголовок і тіло, заздалегідь заповнені з комітів гілки, перемикач
чернетки і — на GitHub — рецензенти, мітки та виконавці, застосовані одразу під
час створення.

![Створення pull-реквеста](../../screenshots/create-pr.webp)

Працює на **GitHub, GitLab, Bitbucket і Azure DevOps**. Відкриті PR/MR для всіх
чотирьох показані на бічній панелі.

Почніть із порівняння гілок, із графа, з `+` у панелі PR або із задачі (яка
підставить `Closes #N`).

## Стеки у списку

Pull requestʼи, що стоять один на одному, згортаються в один рядок: піктограма
стека, гілка, на яку приземляється ланцюг, і скільки їх. Розгорніть — і побачите
ланцюг у порядку читання, від вершини до основи, а під кожним рядком маленьку
стрілку з тим, у що він вливається: напрям на екрані, а не виводиться з чотирьох
баз.

Групу задають дві речі: власний номер стека GitHub, якщо pull requestʼи входять
до [нативного стека](stacks.md), а інакше самі посилання — pull request, чия база
є головою іншого, стоїть на ньому. Друге правило й робить це робочим на GitLab,
Bitbucket та Azure DevOps.

![Стек у списку pull requestʼів](../../screenshots/pr-stack-list.webp)

У кожному рядку — стан **перевірок** його голови (наведіть, щоб побачити числа), а
на GitHub ще й рівні, вже закриті чи влиті, які список відкритих PR сховав би.
Рівень над **закритим** позначається заблокованим: його власні перевірки можуть
бути зеленими, але гілка, на яку він націлений, уже ніколи не приземлиться. Дії
рядка зʼявляються при наведенні, щоб заголовку вистачало ширини.

Читання перевірок коштує один запит на pull request і лише під час оновлення
списку.

## Ваші pull request’и в батьківському репозиторії форка

У форку важливі зазвичай ті pull request’и, які ви відкрили в репозиторії, від
якого зроблено форк, а живуть вони там, а не у вашому форку. Тому, якщо в
репозиторію є віддалений `upstream`, що вказує на інший репозиторій GitHub, ніж
`origin`, список також запитує в `upstream` відкриті pull request’и й лишає
**тільки ті, чия гілка походить із вашого форка**. Вони показуються під pull
request’ами форка, під заголовком із назвою батька, **У owner/repo**. Клік
відкриває той самий екран подробиць, із перевірками й рев’ю, у батьківському
репозиторії.

![Власний pull request форка, а під ним його pull request’и в батьку, під On example/pr-ready-branch](../../screenshots/fork-upstream-prs.webp)

*Обмеження:* лише GitHub і лише віддалений з назвою `upstream`. Інші pull
request’и батька навмисно не показуються: це його черга, а не ваша робота. Стеки
й пошук гілок, як і раніше, працюють лише зі списком `origin`. Запит до батька —
це ще один запит під час кожного оновлення.

## Рев’ю — GitHub і GitLab

![Сторінка pull request’а з обговоренням і бічною панеллю рецензентів](../../screenshots/pull-request-page.webp)

Клік по pull request’у відкриває його **окремою сторінкою**. Вона прив’язана до
свого репозиторію, як вікі: значок із номером PR на вкладці репозиторію або на
його мітці в групі. Натисніть значок ще раз або назву репозиторію, щоб
повернутися. **Відкрити в новій вкладці** в контекстному меню PR дає йому натомість
власну вкладку. Якщо репозиторій ніде не відкрито, PR відкривається в окремій
вкладці.

Робота йде в основній колонці, а бічна панель каже, чим PR *є*, без прокручування.
З увімкненим ШІ кнопка ✨ у заголовку робить рев’ю diff’у PR у тому вигляді, в
якому його віддає хост, — це працює навіть для гілки, яку ви ніколи не
завантажували (форк, чужа гілка).

В основній колонці три розділи:

| Розділ | Що в ньому |
|---|---|
| **Обговорення** | Опис, коментарі й гілки рев’ю по рядках (`файл:рядок`, з відповідями). Далі поле коментаря з «коментувати / схвалити / запросити зміни» і блок злиття (merge, squash або rebase) |
| **Файли** | Кожен змінений файл і diff вибраного поруч зі списком, з підсвічуванням синтаксису та змінами на рівні слів (схожі на секрети файли маскуються, якщо це налаштування ввімкнено). Список ✓ «переглянуто» пам’ятає ваш поступ. Файл, для якого хост не надсилає diff (двійковий або завеликий), веде на хост |
| **Перевірки** | Check-runs CI (GitHub), завдання pipeline (GitLab), статуси коміту (Forgejo) або статуси PR (Azure DevOps) — з результатом і посиланнями на логи |

Бічна панель показує:

| Рядок | Показує |
|---|---|
| **Автор** | Хто відкрив і коли |
| **Статус** | Відкритий, чернетка, злитий (ким, коли) або закритий; конфлікти з цільовою гілкою |
| **Рецензенти** | Останнє рішення кожного рецензента (схвалено, запитано зміни, прокоментовано) і хто ще має переглянути, включно з командами |
| **Виконавці, мітки, віха** | Як задано на хості, мітки у своїх кольорах |
| **Гілки** | Джерело → ціль, і форк, з якого він прийшов |
| **Зміни** | Змінені файли, коміти, додані й вилучені рядки, зі смугою |
| **Перевірки** | Пройдено / провалено / триває, за один клік від розділу «Перевірки» |
| **Учасники** | Усі, хто брав участь |
| **Активність** | Коли відкрито й коли востаннє оновлено |

GitLab не повідомляє підсумки рядків для merge request’у; їх підсумовують зі
списку файлів, коли той завантажиться. Рядок, якого хост не повідомляє, не
показується.

Якщо хтось зробить force-push посеред рев’ю, [що змінилося відтоді](range-diff.md)
покаже, що саме зсунулося.

Відмінності GitLab, прямо: у GitLab немає єдиного виклику «надіслати рев’ю», тому
**схвалити** використовує його endpoint схвалення, а **запросити зміни** знімає
ваше схвалення й публікує коментар. **Rebase-merge** не пропонується — GitLab
вибирає між merge-комітом і fast-forward за налаштуваннями проєкту, тож меню
злиття показує лише merge і squash. Гілки по рядках показують файл і рядок, але
не навколишній шматок diff’у, якого API GitLab не повертає. Рев’ю і злиття
працюють на gitlab.com і на [GitLab на власному сервері](#gitlab-на-власному-сервері).
Bitbucket для рев’ю й надалі відкривається в браузері.

Відмінності Forgejo: гілки коментарів до рядків показуються, але відповісти в них
не можна (у Forgejo немає для цього API), а перевірки — це статуси head-коміту.
Докладніше в розділі [Forgejo](#forgejo).

Відмінності Azure DevOps: схвалення віддає ваш голос (*Approved*); **запросити
зміни** голосує *Waiting for author*. Завершити PR можна через merge, squash або
rebase. Azure перелічує змінені файли PR, але не надсилає diff, тож застосунок
завантажує обидві версії кожного файлу й сам рахує diff — для перших 200 файлів;
двійковий файл або завелика зміна ведуть на хост. Люди показуються ініціалами,
бо фото профілю в Azure потребують браузера з виконаним входом.

Бічна панель також показує **work item’и, пов’язані з PR**, — номер, назву, тип і
стан; кожен відкривається в браузері. Щоб їх прочитати, потрібен токен із
читанням work item’ів (*Work Items: Read*); без нього рядок просто не
показується.

## GitLab на власному сервері

Корпоративний GitLab має власну адресу. Вкажіть її в профілі в **Налаштування →
Інтеграції → GitLab → Адреса GitLab**, наприклад `git.example.org` або
`https://example.net/gitlab` для екземпляра під шляхом. Відтепер віддалені на
цьому хості — це GitLab: merge request’и показуються, відкриваються,
рецензуються й зливаються, браузер клонування та *Створити репозиторій* працюють
із ним, а push і fetch входять із токеном цього профілю.

**Токен GitLab належить одному екземпляру.** Токен профілю надсилається лише на
адресу, вказану в цьому профілі. Порожня адреса означає gitlab.com. Токен
gitlab.com ніколи не потрапляє на корпоративний сервер, а корпоративний — на
gitlab.com. Якщо робочий і особистий облікові записи на різних екземплярах,
дайте кожному свій профіль. Репозиторій, прив’язаний до профілю, використовує
екземпляр цього профілю.

**Створити токен** відкриває сторінку токенів вашого екземпляра з уже вибраними
`api` і `write_repository`. Токен лише для читання підключається без проблем, а
потім падає на першому push.

Обмеження:

- **Лише https.** Адресу `http://` відхилено, бо токен ішов би мережею відкритим
  текстом.
- **Один екземпляр GitLab на профіль.** Для другого екземпляра додайте другий
  профіль.
- Через ssh порівнюється хост, а не шлях, тож два екземпляри на одному хості з
  різними шляхами для ssh-віддаленого не розрізнити.
- Аватари віддалених малюються лише для gitlab.com і github.com. Віддалений на
  власному сервері отримує простий значок, щоб назви його груп ніколи не йшли на
  публічний хост.

## Forgejo

Вкажіть адресу екземпляра перед введенням його токена. Зміна адреси скидає попередній вхід.

![Налаштування інтеграції з Forgejo](../../screenshots/forgejo-integration.webp)

Forgejo — і Gitea, яка має той самий API, — завжди працює за адресою, яку обрав
власник: ваш власний сервер або публічний, як codeberg.org. Вкажіть цю адресу в
профілі в **Налаштування → Інтеграції → Forgejo** разом із токеном доступу.
**Створити токен** відкриває сторінку токенів цього сервера. Дайте токену читання й запис для *repository*, *issue* і *notification* та
читання для *user* і *organization*. Дозволи токена потім не змінюються: токен
без *issue* чи *notification* не покаже ні issues, ні сповіщень, і рішення —
створити новий.

Відтепер віддалені на цьому сервері — це Forgejo:

| Працює | Як |
|--------|----|
| Push і fetch | Вхід із токеном профілю |
| Відкриті pull request’и | У списку бічної панелі, відкриваються на [сторінці pull request’а](#ревю--github-і-gitlab): обговорення, diff кожного файлу, перевірки (статуси коміту, зокрема Forgejo Actions), коментар, схвалення, запит змін, а також merge / squash / rebase |
| Створення pull request’а | Із застосунку; чернетка отримує префікс `WIP:`, який використовує Forgejo |
| Браузер клонування, створення репозиторію | На цьому сервері, під вашим обліковим записом або в організації |

Перевірка, що є завданням **Forgejo Actions**, показує свій лог під рядком — з
кольорами, починаючи з кінця, де помилка. У Forgejo немає API для логів завдань,
тож застосунок запитує ту саму сторінку, що завантажує веб-переглядач логів, і
надсилає токен, лише коли посилання — завдання на цьому самому сервері; статус
зовнішньої CI його ніколи не отримує. Сервер, що віддає логи лише браузеру з
виконаним входом, відповідає сторінкою входу — рядок про це каже й пропонує
браузер. Дуже довгі логи показують останні кілька тисяч рядків.

Як і з GitLab, **токен Forgejo йде лише на сервер, який його видав**. Профіль без
адреси Forgejo не має жодних облікових даних Forgejo. Сервера за замовчуванням,
на який можна було б відкотитися, немає.

Обмеження:

- Гілки коментарів до рядків показуються, але відповісти в них із застосунку не
  можна: у Forgejo немає API для відповіді всередині наявної гілки. Відповідайте
  на сервері.
- Лише https, один сервер Forgejo на профіль.
- Списки зупиняються після двадцяти запитів: 1000 pull request’ів або репозиторіїв за типового розміру сторінки сервера.

## Issues, віхи, релізи — GitHub і Forgejo

Переглядайте задачі й відкривайте повноцінну вкладку задачі: тіло, коментарі,
мітки, виконавці, віха, поля Projects v2, закриття/перевідкриття і **створення
гілки для цієї задачі** (з назвою від ШІ). Віхи показують прогрес і свої задачі.
Релізи можна переглядати разом зі сторінкою змін.

На сервері [Forgejo](#forgejo) працюють ті самі списки й сторінки, з
Forgejo-токеном профілю. Дві речі є лише в GitHub і там лишаються порожніми: поля
Projects v2 і pull request’и, пов’язані з issue. Релізи показуються найсвіжіші, а
не вся історія.

## Чекають на ваше рев’ю

У списку pull request’ів на бічній панелі значок 👁 позначає PR, де **ви** —
рецензент і ще не відповіли, — на GitHub, GitLab і Forgejo однаково. Хто такі
«ви», застосунок дізнається в хоста за обліковими даними профілю й пам’ятає
десять хвилин. Токен, який не може прочитати власного користувача (наприклад, без
`read:user` у Forgejo), нічого не позначає.

З увімкненим **Налаштування → Системні сповіщення** pull request у GitLab чи
Forgejo, що *починає* чекати на вас, викликає сповіщення; клік відкриває сторінку
PR. Перший погляд на репозиторій лише запам’ятовує, що вже чекає, тож запуск
застосунку не програє накопичене. Запити на рев’ю з GitHub лишаються його скриньці
сповіщень, нижче, яка вже про них повідомляє.

## Сповіщення — GitHub і Forgejo

Уся ваша вхідна скринька — запити на рев’ю, згадки, активність CI — по всіх
репозиторіях, із фільтрами непрочитаного/усього та позначенням як прочитане.
Дзвіночок на панелі носить бейдж непрочитаного, а за бажанням спрацьовують і
системні сповіщення, коли у вас просять рев’ю або коли завершується CI.

Якщо в активного профілю є сервер Forgejo, його сповіщення потрапляють до того
самого списку, від нових до старих, і позначаються прочитаними на тому сервері.
Forgejo не каже, *чому* ви отримали сповіщення, тож ці рядки не мають причини й
ніколи не викликають системного сповіщення — його вирішує причина.

## Токени

Окремі токени для кожного профілю — для кількох облікових записів чи організацій
— зберігаються в keychain вашої ОС. Gitcito також уміє позичити те, що вже
тримає ваш **помічник облікових даних git**, тож організація, для якої ви вже
пройшли автентифікацію, часто взагалі не потребує налаштування. Дивіться
[Безпеку та секрети](security.md).

Кожен профіль **прив'язує власний обліковий запис**. У Налаштування →
Інтеграції кнопка **Увійти через git** шукає вхід, який уже є на комп'ютері, — у
credential helper git, далі активний обліковий запис **GitHub CLI**, далі вікно
входу самого helper — і прив'язує цей обліковий запис до профілю. Нічого не
спільне неявно: новий профіль починає без підключення, а обліковий запис, уже
прив'язаний до іншого профілю, відхиляється. Щоб прив'язати другий обліковий
запис GitHub, додайте його в gh (`gh auth login`), зробіть активним
(`gh auth switch`) і увійдіть з іншого профілю — або вставте токен цього
облікового запису. Git ніколи не питає ім'я користувача й пароль у терміналі.

Сторінка показує, що використовує підключення — токен профілю, його прив'язку до
helper git чи до GitHub CLI, а **Від'єднати** скасовує це лише для цього
профілю: токен стирається (на сервісі він діє, доки ви його там не відкличете),
прив'язка знімається (вхід лишається в gh або в helper).

І API сервісу — pull request'и, issues, CI, — і fetch, pull та push самого git
через https використовують токен або прив'язаний обліковий запис профілю.
Облікові дані потрапляють у git лише для цієї однієї команди, лише для хоста
віддаленого репозиторію, і ніколи не записуються в `.git/config`. Профіль без
жодного з них лишає git його власному credential helper. Azure DevOps, GitLab і
Bitbucket прив'язуються через credential helper git — Git Credential Manager
зберігає кілька облікових записів на сервіс — або використовують токен на
профіль. Прив'язка вказує один обліковий запис на сервіс, тож організаціям із
різними обліковими записами потрібен окремий профіль для кожної.
