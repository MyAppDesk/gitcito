# 托管与拉取请求

## 创建

不用离开这个应用就能创建拉取请求（PR，在有些平台上叫合并请求）：分支下拉框、由该分支的提交预填好的标题和正文、一个草稿开关，以及——在 GitHub 上——创建时就一并设好的评审者、标签和指派人。

![创建一个拉取请求](../../screenshots/create-pr.webp)

**GitHub、GitLab、Bitbucket 和 Azure DevOps** 都能用。四家平台上打开着的 PR/MR 都列在侧边栏里。

可以从分支对比、提交图、PR 面板里的 `+`，或者从一个议题出发创建（后者会自动填上 `Closes #N`）。

## 列表里的堆栈

互相叠在一起的 PR 会折叠成一行：堆栈图标、这条链落脚的分支，以及一共几个。展开就能按阅读顺序看到整条链——从最上面一直到基底——每行下面还有个小箭头写着它合并进
哪里，方向直接摆在屏幕上，不用对着四个基底自己推。

决定它们成组的有两件事：如果这些 PR 属于[原生堆栈](stacks.md)，就用 GitHub 自己的堆栈编号；
否则看 ref 本身——基底是另一个 PR 的 head，就说明它压在那个上面。第二条规则正是它在 GitLab、
Bitbucket 和 Azure DevOps 上同样管用的原因。

![PR 列表里的堆栈](../../screenshots/pr-stack-list.webp)

每一行都带着它 head 的**检查**状态——悬停能看到数量——在 GitHub 上还会列出已经关闭或已
合并的层，这些在“只看开着的 PR”的列表里本来是看不到的。位于**已关闭**那层之上的层会被标
成受阻：它自己的检查也许是绿的，但它指向的分支永远不会落地了。行上的操作按钮悬停才出现，
好把宽度让给标题。

读取检查的代价是每个 PR 一个请求，而且只在刷新列表时发生。

## 评审——GitHub 与 GitLab

| | |
|---|---|
| **对话** | 评论与评审状态 |
| **检查** | CI 检查任务（GitHub）或流水线作业（GitLab），带通过／失败／等待中状态和查看日志的链接 |
| **已看过的文件** | 每个文件一个 ✓ 的清单，带进度 |
| **行内讨论串** | 按 `file:line` 归组的行评论，以及回复 |
| **动作** | 评论、批准、要求修改，以及合并 / 压缩合并 |

如果有人在评审进行到一半时强制推送，[自那以后改了什么](range-diff.md)会准确告诉你哪些东西动了。

GitLab 的差别，直说了就是：GitLab 没有单一的“提交评审”调用，所以**批准**用的是它的批准接口，**要求修改**则会撤掉你的批准并发出你的评论。不提供**变基合并**——GitLab 会根据项目设置自行决定用合并提交还是快进，所以合并菜单里只有合并和压缩合并两项。行内讨论串会显示文件和行号，但不会显示周围的变更块，因为 GitLab 的 API 不返回它。评审／合并适用于 **gitlab.com** 上的项目；自托管实例暂不支持。Bitbucket 和 Azure DevOps 的评审仍会在浏览器中打开。

## 议题、里程碑、发布——GitHub

浏览议题，并打开一个完整的议题标签页：正文、评论、标签、指派人、里程碑、Projects v2 字段、关闭／重新打开，以及**为这个议题创建一个分支**（可由 AI 起名）。里程碑会显示进度和它下面的议题。发布可以连同变更日志页面一起浏览。

## 通知——GitHub

你的整个收件箱——评审请求、提及、CI 动态——覆盖每一个仓库，带未读／全部筛选和标记为已读。工具栏上的铃铛带一个未读徽标，还可以选择在有人请求评审或 CI 跑完时弹出桌面通知。

## 令牌

按配置档保存的令牌，可以对应多个账号或组织，存在你操作系统的钥匙串里。Gitcito 也可以直接借用你的 **git credential helper** 里已经有的凭据，所以一个你早就认证过的组织往往完全不需要配置。见[安全与机密](security.md)。

每个配置文件**关联它自己的账号**。在 设置 → 集成 中，**用 git 登录** 会查找
机器上已有的登录——先是 git 的 credential helper，然后是 **GitHub CLI** 的活动
账号，然后是 helper 自己的登录窗口——并把该账号关联到配置文件。不会有任何隐式
共享：新配置文件一开始是未连接的，已被其他配置文件关联的账号会被拒绝。要关联第二
个 GitHub 账号，请把它加入 gh（`gh auth login`），设为活动账号（`gh auth switch`），
再从另一个配置文件登录——或粘贴该账号的令牌。git 永远不会在终端里询问用户名和密码。

页面会显示连接使用的是配置文件的令牌、与 git helper 的关联，还是与 GitHub CLI 的
关联；**断开连接** 只对当前配置文件生效：令牌会被清除（在你于托管方撤销之前仍然
有效），关联会被移除（登录仍保留在 gh 或 helper 中）。

关联用于托管方的 API——拉取请求、议题、CI。git 自身通过 https 的 fetch 和 push 仍
使用配置文件的令牌或 git 的 credential helper；`gh auth setup-git` 会把 gh 注册为
该 helper。Azure DevOps、GitLab 和 Bitbucket 通过 git 的 credential helper 关联
（Git Credential Manager 可为每个托管方保存多个账号），或每个配置文件使用一个令牌。一个关联对应每个托管方的一个账号，因此需要不同账号的组织应各用一个配置文件。
