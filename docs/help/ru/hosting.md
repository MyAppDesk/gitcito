# Хостинги и пул-реквесты

## Создание

Создавайте пул-реквест (или мёрж-реквест), не выходя из приложения: выпадающие
списки веток, заголовок и описание, предзаполненные из коммитов ветки,
переключатель черновика и — на GitHub — ревьюеры, метки и исполнители,
проставляемые прямо при создании.

![Создание пул-реквеста](../../screenshots/create-pr.webp)

Работает с **GitHub, GitLab, Bitbucket и Azure DevOps**. Открытые PR/MR всех
четырёх перечислены в боковой панели.

Начать можно из сравнения веток, из графа, по `+` в панели PR или из задачи
(тогда подставится `Closes #N`).

## Стеки в списке

Pull request’ы, стоящие друг на друге, сворачиваются в одну строку: значок
стека, ветка, на которую приземляется цепочка, и сколько их. Разверните — и
увидите цепочку в порядке чтения, от вершины к основанию, а под каждой строкой
маленькую стрелку с тем, во что она вливается: направление на экране, а не
выводится из четырёх баз.

Группу задают две вещи: собственный номер стека GitHub, если pull request’ы
входят в [нативный стек](stacks.md), а иначе сами ссылки — pull request, чья база
это голова другого, стоит на нём. Второе правило и делает это работающим на
GitLab, Bitbucket и Azure DevOps.

## Ревью — GitHub и GitLab

| | |
|---|---|
| **Обсуждение** | Комментарии и состояние ревью |
| **Проверки** | Прогоны CI (GitHub) или задания пайплайна (GitLab) со статусами успех/провал/в процессе и ссылками на логи |
| **Просмотренные файлы** | Чек-лист с ✓ по каждому файлу и прогрессом |
| **Ветки комментариев** | Комментарии к строкам, сгруппированные по `file:line`, и ответы |
| **Действия** | Комментировать, одобрить, запросить изменения, а также merge / squash |

Если кто-то делает форс-пуш посреди ревью, [что изменилось с прошлого
раза](range-diff.md) покажет вам ровно то, что сдвинулось.

Отличия GitLab, названные прямо: у GitLab нет единого вызова «отправить
ревью», поэтому **одобрить** использует его эндпоинт одобрений, а **запросить
изменения** снимает ваше одобрение и публикует ваш комментарий. **Rebase-merge**
не предлагается — GitLab сам выбирает между merge-коммитом и fast-forward по
настройкам проекта, поэтому в меню мёржа только merge и squash. Ветки
комментариев показывают файл и строку, но не окружающий ханк диффа: API GitLab
его не возвращает. Ревью и мёрж работают для проектов на **gitlab.com**;
self-hosted-инстансы пока не поддерживаются. Bitbucket и Azure DevOps для ревью
по-прежнему открываются в браузере.

## Задачи, вехи, релизы — GitHub

Просматривайте задачи и открывайте полноценную вкладку задачи: описание,
комментарии, метки, исполнители, веха, поля Projects v2, закрытие/переоткрытие и
**создать ветку под эту задачу** (с именованием через ИИ). У вех показывается
прогресс и их задачи. Релизы просматриваются вместе со страницей changelog.

## Уведомления — GitHub

Весь ваш входящий поток — запросы на ревью, упоминания, активность CI — по всем
репозиториям сразу, с фильтрами непрочитанное/все и отметкой о прочтении. На
колокольчике в панели инструментов висит счётчик непрочитанных, а по желанию
приходят и системные уведомления, когда у вас запросили ревью или закончился CI.

## Токены

**git credential helper**, так что организации, для которой вы уже
аутентифицировались, часто вообще не нужна никакая настройка. Смотрите
