# スタックブランチ

スタックとは、それぞれが下のブランチの上に積み上がったブランチの連なりです。
`main → api → ui` のような形です。小さなプルリクエスト 3 つのレビューは、巨大なもの
1 つのレビューに勝ります。

![ブランチスタック](../../screenshots/branch-stack.webp)

Gitcito はスタックを上から下へ、最後に着地するトランクまで描きます。各レベルには自分の
コミット数、**その PR が何をターゲットにするか**（ひとつ下のレベル、最下段はトランク）、
そして提出後は PR 番号がクリックできるチップとして並びます。

## スタックを組む

| これを押すと | こうなります |
|--------------|--------------|
| **レベルを追加** | 先端の上にブランチを作ってチェックアウトします。`gh stack add` そのものですが、必須の引数ではなくピッカーで選びます。 |
| 任意のレベルの**この上に追加** | 同じことをスタックの*途中*で行います。そのレベルの上に乗っていたものは新しいブランチへ張り替えられるので、鎖は順序を保ったまま一段増えます。再生（リプレイ）は不要です — 新しいブランチは親の先端に作られるからです。 |
| **既存のブランチを追加** | すでに持っているブランチが先端の上からスタックに加わります。普通に始めて、あとからスタックだったと気づいたときに便利です。 |

ブランチを入れる欄はすべて**入力補完つき**です。打てば絞り込み、↑/↓ と Enter で確定、
一覧にない文字列もそのまま通るので、`origin/main` のようなリモート追跡参照もベースに
できます。

## 並べ替え

レベルの **↑ / ↓** は隣と入れ替えます。これはメタデータの編集ではありません。鎖を
張り替えて再生するので、各レベル自身のコミットが新しいベースの上に着地します。この
操作は取り消せます（<kbd>⌘Z</kbd>）— 取り消しは以前の順序を再生するだけで、古い
コミットを蘇らせるわけではありません。

並べ替えは rebase の連続なので、restack と同じように**衝突**しえます。Gitcito は最初の
衝突で止まり、衝突ビューを渡します。その下のレベルはすでに移動済みです。

## 別の場所を向ける

レベルの**親を設定**は同じピッカーを開きます。別のブランチを選べば、そのレベルのリンクが
移ります。一番下の**ベース**の行はトランクに対して同じことをします — 変えれば、スタック
全体が新しいトランクに張り替えられて再生されます。

## すべてプッシュ

**すべてプッシュ**は各レベルを `--force-with-lease` でプッシュしてそこで止まります —
何も開かない `gh stack push` です。下の**スタックを PR として提出**は同じプッシュに加えて
PR の作業まで行います。リモートにブランチは置きたいがレビューはまだ、というときは
**すべてプッシュ**を使ってください。

## スタックを連鎖プルリクエストとして提出する

**スタックを PR として提出** は、スタック用ツールが有料で売っている作業をワンクリック
でこなします。

1. すべての段を `--force-with-lease` でプッシュします（新しいブランチはそのままでも
   通りますが、リスタック済みのブランチにはこれが必要です）。
2. プルリクエストのない段すべてにプルリクエストを開きます — それぞれの宛先は `main`
   ではなく **親のブランチ** なので、どのレビューにも自分のコミットだけが表示されます。
   タイトルと説明はその段自身のコミットから作られます。
3. ベースがずれてしまった既存のプルリクエストの宛先を付け替えます。
4. すべてのプルリクエスト本文に **スタックナビゲーションのセクション** を書き込むので、
   どの段のレビュアーも連鎖全体と、そのプルリクエストがその中のどこにあるのかを見渡せ
   ます。

この操作は **冪等** です。リスタック、段の追加、プルリクエストのマージのたびに押しても
結果は収束します — 何も重複せず、ずれたものだけが更新されます。

いちばん下のプルリクエストが**マージ**されたら、同じボタンが後片付けまで引き受けます。
マージ済みの段の子はトランクの上に付け替えられ、その段は追跡解除され、ローカルブランチ
は削除され（トランクがそれを含むことが証明できるので安全です）、連鎖はリスタックされ、
残りのプルリクエストはすべて宛先が付け替えられます。下から順にマージして、提出を押して、
繰り返してください。

## リスタック

下のブランチが変わったとき — `api` でレビュー指摘に対応した、というような場合 — その上の
ブランチはどれも間違ったベースの上に乗っています。**リスタック** は `rebase --onto` で
連鎖全体をリベースし直すので、親を書き換えても子にコミットが重複しません。リスタックの
あとにもう一度 **提出** を押してください。書き換えられた段が強制プッシュされ、プル
リクエストはその場で更新されます。

## 制限

- 提出は今のところ **GitHub のみ** です（作成は 4 つのホストすべてで動きますが、宛先の
  付け替えと本文の更新には GitHub API が必要です）。
- いちばん下のマージ後の後片付けは、マージとリベースによるマージを祖先関係から検出し、
  **スカッシュ**マージは、そのブランチのプルリクエストが取り込まれたかどうかを GitHub に
  問い合わせて検出します — つまり GitHub トークンがあれば、どのマージ方式でも後片付け
  されます。他のホストの場合や、トークンがない場合は、スカッシュマージされた段は今まで
  どおり手動での追跡解除が必要です。また、先にフェッチしてください — 祖先関係の確認は、
  最後にフェッチした時点のトランクを読みます。
- プルリクエスト本文のスタックセクションは隠しマーカーの間で管理されるので、その上に
  書いたあなた自身の説明は保持されます。
- 並べ替えとトランクの変更は、触れたすべてのレベルで**履歴を書き換えます**。ブランチは
  あなたのもので、未プッシュのレベルなら痛みはありませんが、すでにレビュー中のレベルは
  次の提出で強制プッシュを受けます。
- レベルは一度に一段しか動きません。二回の入れ替えは二回の rebase であり、途中で止まった
  状態も読み取れます。三つ先に着地するドラッグはそうはいきません。

## つながりが保存される場所

親へのつながりは **git config** に保存されるので、リポジトリと一緒に移動し、クローンし
直しても残ります。どこかのサービスに置かれるものはありません。
