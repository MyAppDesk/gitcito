# 호스팅과 풀 리퀘스트

## 만들기

앱을 벗어나지 않고 풀 리퀘스트(또는 머지 리퀘스트)를 만들어요. 브랜치 드롭다운,
브랜치의 커밋으로 미리 채워진 제목과 본문, 초안 토글, 그리고 GitHub에서는
생성과 동시에 적용되는 리뷰어·라벨·담당자까지 있어요.

![풀 리퀘스트 만들기](../../screenshots/create-pr.webp)

**GitHub, GitLab, Bitbucket, Azure DevOps** 에서 동작해요. 네 곳 모두의 열린
PR/MR 이 사이드바에 나열돼요.

브랜치 비교, 그래프, PR 패널의 `+`, 또는 이슈에서 시작할 수 있어요. 이슈에서
시작하면 `Closes #N` 이 자동으로 채워져요.

## 목록 속의 스택

서로의 위에 얹힌 풀 리퀘스트는 스택 아이콘, 사슬이 착지하는 브랜치, 개수를 가진 한 줄로
접힙니다. 펼치면 사슬이 읽는 순서대로 — 잎에서 베이스까지 — 보이고, 각 줄 아래에는 무엇에
병합되는지 알려주는 작은 화살표가 붙습니다. 방향이 화면에 있으니 베이스 넷을 보고
추측하지 않아도 됩니다.

그 묶음을 정하는 것은 두 가지입니다. 풀 리퀘스트가 [네이티브 스택](stacks.md)에 속하면
GitHub 자신의 스택 번호이고, 아니면 ref 그 자체입니다 — 베이스가 다른 PR의 head인 것은 그
위에 얹혀 있습니다. 두 번째 규칙 덕분에 GitLab, Bitbucket, Azure DevOps에서도 똑같이
동작합니다.

## 리뷰 — GitHub와 GitLab

| | |
|---|---|
| **대화** | 댓글과 리뷰 상태 |
| **체크** | 통과/실패/대기 상태와 로그 보기 링크가 있는 CI 체크 실행(GitHub) 또는 파이프라인 잡(GitLab) |
| **본 파일** | 파일별 ✓ 체크리스트와 진행률 |
| **인라인 스레드** | `file:line` 별로 묶인 줄 댓글과 답글 |
| **작업** | 댓글, 승인, 변경 요청, 그리고 머지 / 스쿼시 |

리뷰 중에 누군가 강제 푸시를 하면, [그동안 바뀐 것](range-diff.md)이 무엇이
움직였는지 정확히 보여 줘요.

GitLab의 차이를 솔직하게 말하면 이래요. GitLab에는 단일 "리뷰 제출" 호출이
없어서, **승인**은 승인 엔드포인트를 쓰고 **변경 요청**은 내 승인을 거두고
댓글을 올려요. **리베이스 머지**는 제공되지 않아요 — GitLab이 프로젝트 설정에
따라 머지 커밋과 fast-forward 중에서 결정하기 때문에, 머지 메뉴에는 머지와
스쿼시만 보여요. 인라인 스레드는 파일과 줄은 보여 주지만 주변 diff 헝크는 보여
주지 않는데, GitLab API가 그걸 돌려주지 않기 때문이에요. 리뷰/머지는
**gitlab.com** 의 프로젝트에서 동작하고, 자체 호스팅 인스턴스는 아직 지원하지
않아요. Bitbucket과 Azure DevOps는 리뷰할 때 여전히 브라우저로 열려요.

## 이슈, 마일스톤, 릴리스 — GitHub

이슈를 둘러보고 전체 이슈 탭을 열 수 있어요. 본문, 댓글, 라벨, 담당자,
마일스톤, Projects v2 필드, 닫기/다시 열기, 그리고 **이 이슈용 브랜치 만들기**
(AI 이름 짓기 포함)까지요. 마일스톤은 진행률과 그에 속한 이슈를 보여 줘요.
릴리스는 변경 기록 페이지와 함께 둘러볼 수 있어요.

## 알림 — GitHub

리뷰 요청, 멘션, CI 활동까지 모든 저장소에 걸친 받은 편지함 전체를 볼 수 있어요.
읽지 않음/전체 필터와 읽음 표시가 있고요. 툴바의 종에는 읽지 않음 배지가 붙고,
원한다면 리뷰가 요청되거나 CI가 끝났을 때 데스크톱 알림이 뜨게 할 수 있어요.

## 토큰

여러 계정이나 조직을 위한 프로필별 토큰이 OS 키체인에 저장돼요. Gitcito는
**git credential helper** 가 이미 갖고 있는 것을 빌려 쓸 수도 있어서, 이미
인증해 둔 조직이라면 설정이 아예 필요 없는 경우가 많아요.
[보안과 비밀](security.md)을 보세요.
