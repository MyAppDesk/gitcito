# 스택 브랜치

스택은 각 브랜치가 아래 브랜치 위에 쌓이는 사슬이에요. `main → api → ui` 처럼요.
작은 PR 세 개를 리뷰하는 편이 거대한 PR 하나를 리뷰하는 것보다 나아요.

![브랜치 스택](../../screenshots/branch-stack.webp)

Gitcito는 이것을 **경로**로 그립니다. 맨 위에 시작 브랜치, 그 아래로 레벨마다 정류장이
하나씩. 각 정류장의 PR은 바로 위 정류장을 대상으로 하고, 첫 정류장은 시작 브랜치에
착지합니다. 정류장에는 자기 커밋 수, restack이 필요한지, 그리고 제출한 뒤에는 PR 번호가
표시됩니다.

## 경로 편집하기

| 컨트롤 | 하는 일 |
|--------|---------|
| **시작** 필드 | 스택이 착지하는 곳입니다. 바꾸면 사슬 전체가 새 브랜치에 다시 연결되고 재생됩니다. |
| **정류장** 필드 | 그 자리를 차지하는 브랜치를 바꿉니다. 경로에서 빠진 브랜치는 추적만 해제되고 삭제되지 않습니다. |
| **↑ / ↓** | 정류장을 한 칸 옮깁니다. |
| **✕** | 정류장을 경로에서 뺍니다. 앞뒤 정류장이 이어집니다. |
| **정류장 추가** | 이미 있는 브랜치를 고르면 경로 맨 위에 합류하고, 아직 없는 이름을 입력하면 마지막 정류장의 끝에서 만들어져 체크아웃됩니다. |
| 화살표 버튼 | 그 정류장을 체크아웃합니다. |

모든 필드는 입력하며 걸러내기를 지원합니다. 입력하면 걸러지고, ↑/↓와 Enter로 고르며,
목록에 없는 것을 입력해도 그대로 쓰입니다 — 그래서 `origin/main` 같은 원격 추적 참조도
시작 브랜치가 됩니다.

속을 보면 이 편집들은 모두 *같은* 작업입니다. 경로 전체를 한 번에 넘기는 것이죠. 그래서
한 동작이 되돌리기 하나(<kbd>⌘Z</kbd>)이지, 절반만 적용된 링크의 흔적이 아닙니다.

## 경로 편집의 대가

순서를 바꾸는 것은 무엇이든 — 교환, 이동, 다른 시작점 — 사슬을 **다시 재생**합니다. 각
정류장의 커밋이 새 베이스 위로 rebase되기 때문입니다. 그러니 restack과 똑같이 **충돌**할
수 있습니다. 같은 줄을 건드리는 두 정류장은 사람 없이는 자리를 바꿀 수 없습니다. 그럴 때는
**아무 일도 일어나지 않습니다**. 편집 전체가 되돌려지고(끝점도, 부모 링크도, 하다 만 rebase도),
부딪힌 두 정류장의 이름을 알려줍니다. 살짝 건드린 드롭다운 때문에 rebase 한복판에 남겨져서는
안 되니까요.

**Restack**은 그 거래의 나머지 절반입니다. 이름을 대고 요청한 rebase이므로 충돌에서 멈추고 충돌
화면을 넘겨줍니다 — 그것이 Gitcito가 거절한 순서 바꾸기를 이루는 길이기도 합니다. 거기서 해결한
뒤 정류장을 옮기세요.

되돌리기는 이전 경로를 다시 재생합니다. 옛 커밋을 되살리지는 않습니다 — 새 커밋은 부모만
다른 같은 작업이니까요.

## 전체 푸시

**전체 푸시**는 각 레벨을 `--force-with-lease`로 푸시하고 거기서 멈춥니다 — 아무것도 열지
않는 `gh stack push`입니다. 아래의 **스택을 PR로 제출**은 같은 푸시에 PR 작업까지 합니다.
브랜치는 원격에 올리되 아직 리뷰는 원하지 않을 때 **전체 푸시**를 쓰세요.

## 스택을 연쇄 PR로 제출하기

**스택을 PR로 제출**은 스택 도구들이 돈을 받고 파는 일을 클릭 한 번으로 해내요.

1. 모든 단계를 `--force-with-lease` 로 푸시해요(새 브랜치는 그냥 받아들이고,
   재적재된 브랜치에는 이게 꼭 필요해요).
2. PR이 없는 모든 단계에 PR을 열어요 — 각각 `main` 이 아니라 **부모 브랜치를
   기반으로** 하기 때문에, 모든 리뷰에는 자기 커밋만 보여요. 제목과 설명은 그
   단계 자신의 커밋에서 만들어져요.
3. 기반이 어긋난 기존 PR의 대상을 바로잡아요.
4. 모든 PR 본문에 **스택 내비게이션 섹션**을 적어 넣어서, 어느 단계의 리뷰어든
   사슬 전체와 이 PR이 그 안 어디에 있는지 볼 수 있어요.

이 동작은 **멱등**이에요. 재적재하거나 단계를 새로 얹거나 PR이 병합될 때마다
눌러도 결과는 수렴해요 — 아무것도 중복되지 않고, 어긋난 것만 손대요.

맨 아래 PR이 **병합**되면 같은 버튼이 뒷정리까지 해 줘요. 병합된 단계의 자식은
트렁크 위로 부모가 바뀌고, 그 단계는 추적이 해제되고, 로컬 브랜치는 삭제돼요
(안전해요 — 트렁크가 그걸 담고 있다는 게 증명되니까요). 그리고 사슬이 재적재되고
남은 PR의 대상이 모두 바로잡혀요. 아래에서 위로 병합하고, 제출을 누르고,
반복하세요.

## 재적재

아래쪽 브랜치가 바뀌면 — 예를 들어 `api` 의 리뷰 의견을 반영했다면 — 그 위의 모든
브랜치는 이제 잘못된 기반 위에 놓여 있어요. **재적재**는 `rebase --onto` 로 사슬
전체를 연쇄적으로 리베이스해서, 부모를 다시 쓴 결과가 자식들에 커밋을 중복시키지
않도록 해요. 재적재한 뒤에는 **제출**을 다시 누르세요. 다시 쓴 단계들이 강제
푸시되고 PR들이 제자리에서 갱신돼요.

## 한계

- 제출은 아직 **GitHub 전용**이에요(생성은 네 호스트 모두에서 되지만, 대상 변경과
  본문 갱신에는 GitHub API가 필요해요).
- 맨 아래 병합 뒤처리는 merge와 rebase 병합은 조상 관계로 알아보고,
  **스쿼시(squash)** 병합은 그 브랜치의 PR이 병합됐는지 GitHub에 물어봐서
  알아봐요 — 그래서 GitHub 토큰만 있으면 어떤 병합 방식이든 정리돼요. 다른
  호스트에서, 또는 토큰이 없으면 스쿼시로 병합된 단계는 여전히 직접 추적을
  해제해야 해요. 그리고 먼저 페치하세요 — 조상 관계 확인은 마지막 페치 시점의
  트렁크를 읽어요.
- PR 본문의 스택 섹션은 숨은 표식 사이에서 관리돼요 — 그 위에 적은 여러분의 설명은
  그대로 보존돼요.
- 순서 바꾸기와 트렁크 교체는 건드리는 모든 레벨에서 **히스토리를 다시 씁니다**.
  브랜치는 여러분 것이고 아직 푸시하지 않은 레벨은 대가가 없지만, 이미 리뷰 중인 레벨은
  다음 제출에서 강제 푸시를 받습니다.
- 레벨은 한 번에 한 칸씩만 움직입니다. 두 번의 교환은 두 번의 rebase이고, 중간에 멈춘
  상태도 읽을 수 있습니다. 세 칸 건너에 떨어지는 드래그는 그렇지 않습니다.
- 정류장은 **rebase**됩니다. 그래서 스택이 착지하는 브랜치가 동시에 정류장이 되는 일은
  없고, **보호된** 브랜치도 마찬가지입니다(목록을 바꾸지 않았다면 `main`과 `master`). 둘 다
  공유된 히스토리를 조용히 다시 쓰는 대신 거부됩니다.
- 제출은 무언가를 열기 전에 원격에 어떤 브랜치가 실제로 도착했는지 묻고, 도착하지 않은
  것을 이름으로 알려줍니다. head가 없을 때 GitHub이 주는 답은 맨숭맨숭한 "Validation
  Failed"뿐이고, 그건 누구에게도 도움이 안 됩니다.

## 연결 정보가 있는 곳

살아남아요. 어떤 서비스에도 아무것도 남지 않아요.
