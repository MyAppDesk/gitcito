# אירוח ובקשות משיכה

## יצירה

צרו בקשת משיכה (או מיזוג) בלי לצאת מהאפליקציה: רשימות ענפים נפתחות, כותרת וגוף
שממולאים מראש מהקומיטים של הענף, מתג טיוטה, וב־GitHub גם סוקרים, תוויות ומשויכים
שמוחלים בעת היצירה.

![יצירת בקשת משיכה](../../screenshots/create-pr.webp)

עובד ב־**GitHub, GitLab, Bitbucket ו־Azure DevOps**. בקשות פתוחות בכל הארבעה
מופיעות בסרגל הצד.

התחילו אחת מהשוואת ענפים, מהגרף, מה־`+` בפאנל בקשות המשיכה, או מתוך בעיה (שממלאת
`Closes #N`).

## ערימות ברשימה

Pull requests שיושבים זה על זה מתקפלים לשורה אחת עם סמל ערימה, הענף שעליו
השרשרת נוחתת, וכמה יש. פתחו אותה כדי לראות את השרשרת בסדר הקריאה — מהעלה למטה עד הבסיס — עם חץ קטן מתחת
לכל שורה שאומר לאן היא ממוזגת, כך שהכיוון על המסך ולא מוסק מארבעה בסיסים.

שני דברים יוצרים את הקבוצה: מספר הערימה של GitHub עצמו, כשה־pull requests שייכים
ל[ערימה מובנית](stacks.md), ואחרת ה־refs עצמם — pull request שהבסיס שלו הוא
ה־head של אחר יושב עליו. הכלל השני הוא הסיבה שזה עובד גם ב־GitLab, ב־Bitbucket
וב־Azure DevOps.

![ערימה ברשימת ה־pull requests](../../screenshots/pr-stack-list.webp)

כל שורה נושאת את מצב ה**בדיקות** של ה־head שלה — ריחוף מציג את המספרים — וב־GitHub
גם את השכבות שכבר נסגרו או מוזגו, שרשימת PR פתוחים הייתה מסתירה. שכבה שמעל שכבה
**סגורה** מסומנת כחסומה: הבדיקות שלה עשויות להיות ירוקות, אבל הענף שהיא מכוונת אליו
כבר לא ינחת. פעולות השורה מופיעות בריחוף, כדי שהכותרת תשמור על הרוחב.

קריאת הבדיקות עולה בקשה אחת לכל pull request, ורק כשהרשימה מתרעננת.

## סקירה — GitHub ו־GitLab

| | |
|---|---|
| **שיחה** | תגובות ומצב הסקירה |
| **בדיקות** | ריצות בדיקה של CI (GitHub) או משימות pipeline (GitLab) עם עבר/נכשל/ממתין וקישורים ללוגים |
| **קבצים שנצפו** | רשימת ✓ לכל קובץ עם התקדמות |
| **שרשורים בשורה** | תגובות שורה מקובצות לפי `file:line`, ותשובות |
| **פעולות** | תגובה, אישור, בקשת שינויים, ומיזוג / מעיכה |

אם מישהו דוחף בכוח באמצע הסקירה, [מה השתנה מאז](range-diff.md) מראה לכם בדיוק מה
זז.

ההבדלים של GitLab, בגלוי: ל־GitLab אין קריאה אחת של "שליחת סקירה", ולכן
**אישור** משתמש בנקודת הקצה של האישורים שלו, ו**בקשת שינויים** מסירה את האישור
שלכם ומפרסמת את התגובה שלכם. **מיזוג בריבייס** אינו מוצע — GitLab מחליט בין
קומיט מיזוג ל־fast-forward לפי הגדרות הפרויקט, ולכן תפריט המיזוג מציג רק מיזוג
ומעיכה. שרשורים בשורה מציגים את הקובץ ואת השורה אך לא את קטע הדיף שמסביב, שה־API
של GitLab אינו מחזיר. סקירה/מיזוג עובדים לפרויקטים ב־**gitlab.com**; מופעים
באירוח עצמי עדיין אינם נתמכים. Bitbucket ו־Azure DevOps עדיין נפתחים בדפדפן
לצורך סקירה.

## בעיות, אבני דרך וריליסים — GitHub

דפדפו בבעיות ופתחו לשונית בעיה מלאה: גוף, תגובות, תוויות, משויכים, אבן דרך, שדות
Projects v2, סגירה/פתיחה מחדש, ו**יצירת ענף לבעיה הזו** (עם מתן שם בעזרת AI).
אבני דרך מציגות התקדמות ואת הבעיות שלהן. ריליסים ניתנים לדפדוף עם עמוד יומן
שינויים.

## התראות — GitHub

כל תיבת הדואר הנכנס שלכם — בקשות סקירה, אזכורים, פעילות CI — בכל המאגרים, עם
מסנני לא־נקרא/הכול וסימון כנקרא. הפעמון בסרגל הכלים נושא תג של לא־נקראות, והתראות
שולחן עבודה לבחירתכם נורות כשמתבקשת סקירה או כש־CI מסתיים.

## טוקנים

טוקנים לכל פרופיל עבור כמה חשבונות או ארגונים, נשמרים במחזיק המפתחות של מערכת
ההפעלה. Gitcito יכול גם לשאול את מה ש**עוזר האישורים** של git שלכם כבר מחזיק, ולכן
ארגון שכבר התאמתם מולו לרוב אינו דורש שום הגדרה. ראו
[אבטחה וסודות](security.md).

כל פרופיל **מקשר חשבון משלו**. בהגדרות → אינטגרציות, **התחברות באמצעות git** מחפש
התחברות שכבר קיימת במחשב — ב-credential helper של git, אחר כך בחשבון הפעיל של
**GitHub CLI**, ואחר כך בחלון ההתחברות של ה-helper עצמו — ומקשר את החשבון הזה
לפרופיל. שום דבר לא משותף במובלע: פרופיל חדש מתחיל מנותק, וחשבון שפרופיל אחר
כבר קישר נדחה. כדי לקשר חשבון GitHub שני, הוסיפו אותו ל-gh (`gh auth login`),
הפכו אותו לפעיל (`gh auth switch`) והתחברו מהפרופיל האחר — או הדביקו את האסימון
של החשבון הזה. git אף פעם לא מבקש שם משתמש וסיסמה בטרמינל.

הדף מציג אם החיבור הוא האסימון של הפרופיל, הקישור שלו ל-helper של git או הקישור
שלו ל-GitHub CLI, ו**ניתוק** מבטל זאת רק לפרופיל הזה: אסימון נמחק (הוא נשאר בתוקף
אצל הספק עד שתבטלו אותו שם), קישור מוסר (ההתחברות נשארת ב-gh או ב-helper).

הקישורים חלים על ה-API של הספק — בקשות משיכה, issues, CI. ה-fetch וה-push של git
עצמו ב-https עדיין משתמשים באסימון של הפרופיל או ב-credential helper של git;
`gh auth setup-git` רושם את gh כ-helper הזה. Azure DevOps, GitLab ו-Bitbucket
מתקשרים דרך ה-credential helper של git — Git Credential Manager שומר כמה חשבונות
לכל ספק — או משתמשים באסימון לכל פרופיל. קישור מציין חשבון אחד לכל ספק, ולכן ארגונים שדורשים חשבונות שונים מקבלים פרופיל נפרד לכל אחד.
